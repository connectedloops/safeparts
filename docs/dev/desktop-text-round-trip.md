# Experimental desktop text and file round trip

Issue 140 adds a reviewable native slice, not a desktop release. The accepted visual direction is [issue 140 comment 5747267572](https://github.com/connectedloops/safeparts/issues/140#issuecomment-5747267572). The source fixture remains available on `prototype/desktop-reference-ui` at `874c5e7`; production code does not import it.

## Run and test

Use synthetic text and binary files only.

```bash
mise run desktop:test
mise run desktop:run
```

The first command builds the Rust adapter and generated CXX source, compiles the Qt app with warnings denied, and runs the public CXX and Qt action suites. The second command builds and opens the same app.

Rust owns generated packets, recovery validation and state, authoritative recovered bytes, and the Argon2id and ChaCha20-Poly1305 policy for passphrase protection. Qt owns presentation and explicit OS I/O. It retains bounded editor text and at most one selected file Secret, generated Recovery share views, and Combine editors. Generated shares are encoded one at a time on the serialized worker when the complete set fits the checked 160 MiB presentation budget. Larger valid sets remain available through fresh authoritative Copy or Save requests; the UI reveals only the last exported share instead of retaining the set. After a Combine edit, the UI sends every complete nonempty field to the serialized worker, which resets and rebuilds Rust recovery state before returning one readiness result. Sensitive queued and selected-file bytes use `SecureByteBuffer`; its final shared owner overwrites the sole `QByteArray` allocation before release, including buffers still queued when the receiver is destroyed. Recovery admission uses checked arithmetic for current Rust-owned state and the next parser phase, including conservative pre-parse decoded storage, incoming bridge/Qt copies, parser workspace, and fixed UI/runtime headroom. The generated interface uses consuming `destroy_operation`; CXX vectors own returned copies. Every fallible operation entry catches Rust unwinds and returns a content-free status. The only `unsafe_code = "allow"` exception belongs to generated `cxx::bridge` expansion and is pinned by `crates/safeparts_desktop_bridge/scripts/policy_guard.sh`; handwritten operation code remains `forbid(unsafe_code)`.

## Implemented slice

- Split either UTF-8 text or one exact-byte file into V2 Base64url, Base58check, Words, or BIP-39 recovery shares. File reads use the actual streamed bytes and stop after the inclusive operation limit plus one byte, so size metadata and growth during a read cannot cause truncation. Empty file creation is rejected. The source filename and filesystem metadata never enter the share packets.
- Optional passphrase protection is off by default. When enabled, Split requires an exact, nonempty confirmation and uses the same byte-oriented Rust operation for text and files. Words remains the default under Additional options. Text Secret admission converts CRLF and lone CR to LF without trimming or Unicode normalization; file and passphrase bytes remain exact.
- Keep the admitted text Secret, or the selected file name and byte count, above the generated Recovery shares. Every row has Copy and Save actions backed by a fresh authoritative encoding of the retained packet. Repeated exports preserve the same set and share identities. The full set is shown only within the checked presentation budget; larger sets reveal at most the last exported share.
- Save writes one complete encoded recovery share directly to the selected file. There is no temporary staging, rename, rollback, automatic open, or source-file mutation. A cancelled dialog leaves the operation unchanged. Open, zero/short, write, flush, and close failures report failure and preserve the operation; a partial selected destination can remain.
- Start Combine with two numbered Recovery share editors. Paste or load complete UTF-8 share-text batches up to 16 MiB each. File acquisition is transactional: cancelled, unreadable, empty, oversized, or invalid-UTF-8 selections do not change the accepted fields. Loaded LF/CRLF and wrapped mnemonic framing reaches the same strict core parser as pasted input. Empty placeholders remain visible but do not override the core's distinct-share readiness result.
- Use core Auto encoding or an explicit share encoding to inspect unprotected V1/V2 and protected V2 input. Rust metadata decides readiness from every supplied nonempty batch. Malformed or trailing content, duplicates, mixed encodings or versions, mixed sets, unsupported versions or KDF parameters, excessive counts, and limits block recovery without silent filtering or repair. Unsupported or excessive KDF parameters are rejected before KDF work; stored parameters and packet metadata are never lowered or changed.
- Every successful recovery, including valid empty legacy output, offers Save backed by fresh Rust-authoritative bytes. Valid UTF-8 also has inert display and authoritative Copy. Arbitrary binary is Save-only, without replacement characters or guessed encoding. BOM, CRLF, NUL, composed and decomposed Unicode, whitespace, and file-origin UTF-8 bytes save unchanged. Saved output is never opened or executed automatically.
- Reject stale worker and export results by generation after Secret, split-setting, Recovery share, or passphrase edits, plus mode changes, Start over, and close. Failed protected retries expose no output. Lifecycle reset clears app-owned file, passphrase, pending destination, and presentation state; cancellation preserves the current operation.
- Passphrase editors are exact, masked, limited to 1 MiB of valid UTF-8, and expose no copy action or undo history. Missing passphrases remain a specific readiness condition. Wrong-passphrase and uncertain decryption failures share one content-free message and keep inputs available for correction.
- Immutable synthetic corpora cover UTF-8 and arbitrary-byte interoperability. The binary corpus pins unprotected output from desktop, CLI, TUI, and generated real WASM, plus protected desktop output, in all four encodings. Core and every applicable active boundary recover the exact 11-byte binary Secret. This is boundary evidence, not a claim that the web UI exposes binary files or protected file workflows.

Printing, packaging, issue 147 capacity certification, and issues 148 through 151 platform qualification remain outside this slice.

## Clipboard acquisition blocker

The development-host adapter calls `-[NSPasteboard dataForType:]`, which returns a complete `NSData`. `NSPasteboardItem` type discovery reports available types but exposes payload bytes through the same complete-data call; AppKit has no supported byte-length query, ranged read, or stream for a string pasteboard item. The fallback Qt interface, `QMimeData::data()`, likewise returns a complete `QByteArray`. The adapter can avoid creating a Qt `QString` until after checking `NSData.length`, but it cannot enforce the 16 MiB limit before AppKit materializes the payload. That check is intentionally documented as post-acquisition and does not satisfy the required pre-materialization clipboard gate.
