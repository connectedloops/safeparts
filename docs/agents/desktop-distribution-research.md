# Offline desktop distribution: research evidence

- Scope: [Wayfinding: define a new offline Safeparts desktop app](https://github.com/connectedloops/safeparts/issues/126), [Research offline desktop installation and update constraints](https://github.com/connectedloops/safeparts/issues/133); both read through `gh` on 2026-09-19.
- Access date for **all external sources: 2026-09-19 (UTC)**. These are living documents, not price quotations or compatibility commitments.
- Status: internal research, not a channel, framework, OS-minimum, architecture, or spending decision. No current/retired app implementation was consulted. No product support or release policy changes.
- Labels: **Fact** = primary documentation; **Inference** = consequence for this scope; **Unknown** = requires a later decision, quote, or experiment. Unlabelled recommendations below are proposed verification work, not tested results.

## Bottom line

**Inference:** A self-contained, offline installation/first launch is plausible on all three platforms, but only for a declared and tested host baseline. A downloaded file is not necessarily a complete offline installer. macOS needs its notarization ticket carried with the distribution; Windows needs trusted signing and all applicable runtime/dependency payloads; Linux needs an explicit dependency and packaging baseline. [A1][W1][W3][W5][L1][L3]

**Fact:** Apple documents online Gatekeeper checks; Windows documents OS certificate/revocation connections; WebView2 Evergreen updates independently; Flatpak can consult both removable media and the Internet when online. [A2][W4][W3][L2]

**Inference:** “No app-initiated network requests” must not be presented as “this computer never contacts the network,” “the installer never contacts the network,” or “initial acquisition needs no connected party.” Bundling a runtime that updates separately can satisfy a narrow process boundary while violating a user's reasonable expectation; the runtime/helper boundary remains a decision. The approved app must not trigger checks or delegate its updater to a helper as a loophole.

An offline first-launch claim means successful use with networking unavailable, not proof of no attempted requests when networking is available.

## Authenticity, integrity and offline trust

- **Fact:** Developer ID verification checks origin and modification; MSIX requires device trust as well as a signature. Microsoft recommends timestamping: without it an expired signing certificate prevents new installation, though an already installed package continues to run. These statements do not override revocation or policy checks. [A2][W1]
- **Fact:** valid Windows signing does not buy guaranteed warning-free first downloads. Microsoft's current guidance says OV/EV do not bypass SmartScreen; new signed binaries may still warn, and managed policies may prevent proceeding. [W2]
- **Fact:** APT's chain depends on securely acquiring the repository key and does not protect against compromise of the signing key or archive master. AppImage needs verification independent of the untrusted executable itself; RPM provides package verification with its keyring. [L6][L5][L7]
- **Inference:** publish versioned artifacts, sizes, checksums and authenticated release metadata outside the app. A hash obtained from the same compromised location as an unsigned binary only proves consistency with that location, not publisher identity. Document publisher identity and trustworthy key acquisition; signing alone does not establish that an old artifact is the latest secure version.
- **Inference:** an air-gapped machine cannot obtain newly issued revocation/security information without an external transfer. Distinguish “signature checks against available trust material” from “current global trust/security status.” Timestamping preserves evidence of signing time; it does not make a vulnerable build safe forever.
- **Unknown:** the workable verification UX for nontechnical users, including a fresh disconnected machine with stale trust roots, incorrect clock, expired certificate, revoked certificate, or enterprise controls. Do not promise silent installation or a universal offline pass from documentation alone.

## Manual updates, rollback and security servicing

**Approved constraint:** updates are obtained outside the app; no in-app checks/downloads. [Wayfinding: define a new offline Safeparts desktop app](https://github.com/connectedloops/safeparts/issues/126)

| Pattern | Viability / tradeoff (inference unless marked fact) |
| --- | --- |
| Versioned full offline replacement/installer acquired in an external browser or transferred on media | Avoids a bootstrap download and makes a verified previous build retainable. Every release must include required runtime/resources and trust metadata. User awareness and completing the manual update become the security bottleneck. |
| OS/store/repository-managed installation and updates | Can reduce manual servicing burden, but host networking and update scheduling are then externally controlled. **Fact:** App Installer supports launch-triggered checks, background checks every eight hours, and updates that block activation. These are not an automatic fit for the no-network/offline-launch promise. [W6] |
| Offline media containing app plus runtimes/local repository | Useful for disconnected users, with larger media and key/metadata freshness obligations. **Fact:** Flatpak supports offline installation/update from prepared media; it can also target a previous commit. Availability of the commit/dependencies still matters. [L2][L8] |

**Fact:** App Installer normally advances to higher versions; its `ForceUpdateFromAnyVersion` option permits downgrades. This is a packaging-specific mechanism, not evidence that all Windows installers safely roll back. [W6]

**Inference:** rollback may restore recovery availability after a regression, but can reintroduce known vulnerabilities. No sensitive app history reduces data-migration concerns; it does not prove compatibility of preferences, runtimes, OS registrations, or exported share formats. A prior build must remain authenticated and must be tested with existing supported shares. Retaining vulnerable builds indefinitely is a security policy decision, not a free benefit of portable delivery.

**Later decisions:** support/security-fix window; how people learn externally about critical updates; availability and labeling of older artifacts; permissible downgrade paths; whether an external OS-managed update channel is acceptable; responsibility for patching bundled runtimes. Avoid mandatory online activation/version checks to enforce freshness: they conflict with the approved recovery tool's offline use.

## Decision-changing gaps and bounded next checks

1. **Host baseline:** choose candidate OS versions, architectures, Linux families and managed-device policy scope later. Then test fresh standard-user hosts—not machines with developer runtimes already installed. No minimums are selected by this note.
2. **Meaning of no-network:** settle whether runtime/helper-initiated background requests, installer requests, launch-associated OS checks and OS-managed updates are acceptable and how users are told. Preserve the approved prohibition on app-initiated requests. No policy-disabling workaround is proposed.
3. **Release artifact proof:** for each candidate, transfer final signed artifacts to a fresh disconnected host and install/launch with empty caches and missing optional runtimes. Exercise text/file input, existing-share recovery, export, local printing and copy/paste. Record prerequisites, permissions, prompts and failures. These tests have **not** been performed.
4. **Network attribution:** separately run connected observation from installation through first launch/use/close, attributing traffic to app, child runtime, installer, trust services and background OS components. “Worked with the cable unplugged” does not establish no app requests when connected. No packet capture or process tracing has been done.
5. **Trust failures and age:** test tampering, missing stapled ticket, expired/timestamped signing, stale roots and offline policy behavior. Validate authenticity without first running an untrusted AppImage. Define handling of revoked/vulnerable old builds; sources alone do not settle fail-open/fail-closed behavior across hosts.
6. **User-directed output boundary:** printing and clipboard/cloud-sync services can involve OS facilities outside the process. Network printers, spooling, clipboard history/sync, crash reports, swap and installer logs require threat-model/UX work; this distribution research does not certify no sensitive host persistence or no outbound sensitive data. Required printing/copy/export are not quietly removed.
7. **Update and rollback rehearsal:** select representative manual install/replace and downgrade routes, test permissions and interruption, and verify recovery interoperability. Decide external security notification and supported rollback policy with the human owner.
8. **Procurement/source freshness:** resolve public-signing eligibility using the actual publisher region/entity; obtain current localized quotes only if that route is shortlisted. If Store delivery becomes a candidate, investigate enrollment, offline licensing/export and update/rollback constraints separately.
