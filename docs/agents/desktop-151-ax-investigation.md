## Primary-source trace

Apple defines `AXUIElementCreateApplication(pid)` as creating the **top-level accessibility object for that PID**. `AXUIElementGetPid` reports the process associated with an element. `AXUIElementCopyAttributeValue` returns an attribute's value and distinguishes unsupported/no-value/invalid-element/messaging failures. `AXWindows` and `AXFocusedWindow` are application-specific attributes, while `AXChildren` defines the visual hierarchy and requires a child's `AXParent` to point back to its sole parent. See Apple's [AXUIElement API](https://developer.apple.com/documentation/applicationservices/axuielement) and the SDK declarations in `AXUIElement.h` and `AXAttributeConstants.h` (the installed SDK documents these contracts at lines 356–362, 365–380, 515–532, and 1002–1009).

Qt 6.9.1 does not replace the native application or window AX objects with a `QMacAccessibilityElement`: it explicitly ignores Qt `Application` and `Window` roles because it uses the system-provided objects ([`qcocoaaccessibility.mm` lines 210–240](https://github.com/qt/qtbase/blob/v6.9.1/src/plugins/platforms/cocoa/qcocoaaccessibility.mm#L210-L240)). A system query entering `QNSView` activates Qt accessibility, obtains the `QWindow::accessibleRoot()`, assigns/cache-registers its Qt accessible ID, and returns that object as the view's only unignored child ([`qnsview_accessibility.mm` lines 16–49](https://github.com/qt/qtbase/blob/v6.9.1/src/plugins/platforms/cocoa/qnsview_accessibility.mm#L16-L49)). Thus the intended public path is:

`native AXApplication -> native AXWindow -> ignored QNSView -> QMacAccessibilityElement(accessibleRoot) -> Qt widget children`.

For Qt elements, children are generated from `QAccessibleInterface::child()` and stable IDs, then passed through `NSAccessibilityUnignoredChildren` ([`qcocoaaccessibility.mm` lines 264–284](https://github.com/qt/qtbase/blob/v6.9.1/src/plugins/platforms/cocoa/qcocoaaccessibility.mm#L264-L284)). Parents are translated back toward a native view/window when the Qt parent is the application ([`qcocoaaccessibilityelement.mm` lines 595–640](https://github.com/qt/qtbase/blob/v6.9.1/src/plugins/platforms/cocoa/qcocoaaccessibilityelement.mm#L595-L640)). IDs/interfaces are lazily created and cached by object/metaobject; object destruction removes all matching entries and invalidates the native wrapper ([`qaccessible.cpp` lines 722–804](https://github.com/qt/qtbase/blob/v6.9.1/src/gui/accessible/qaccessible.cpp#L722-L804), [`qaccessiblecache.cpp` lines 103–183](https://github.com/qt/qtbase/blob/v6.9.1/src/gui/accessible/qaccessiblecache.cpp#L103-L183), [`qcocoaaccessibilityelement.mm` lines 200–255](https://github.com/qt/qtbase/blob/v6.9.1/src/plugins/platforms/cocoa/qcocoaaccessibilityelement.mm#L200-L255)). There is no eager plugin-initialization requirement in this Cocoa entry path: the first native view query calls `setActive(true)` and asks for the accessible root.

The app constructs one stack-owned `DesktopWindow`, calls `show()`, and enters `app.exec()` (`apps/desktop/src/main.cpp:19-31`); its constructor builds the UI synchronously after setting the window title/size (`apps/desktop/src/desktop_window.cpp:291-334`). No custom top-level native view, accessibility root, application delegate, or accessibility factory is installed. The bundle plist contains ordinary identity/version keys and no accessibility override. The workflow launches the exact relocated executable directly with a scrubbed `QT_`/`DYLD_` environment, rather than asking LaunchServices to select an app by bundle ID (`apps/desktop/scripts/run_package_workflows.py:327-333`).

### Exact known Qt fix adjacent to, but not proven to cause, this symptom

Qt commit [`5dc261357e44`](https://github.com/qt/qtbase/commit/5dc261357e44ac9e15423997748e28ae659a3623) (QTBUG-137157, picked to 6.9 and first present in tag v6.9.2) fixes Qt 6.9.1 returning no valid `AXWindow` **for a descendant Qt accessibility element**. In 6.9.1, `QMacAccessibilityElement::accessibilityWindow` recursively asks its parent for a window, while `accessibilityParent` only falls through to the native `NSView` for an application parent. The fix also treats a Qt `Window` parent as a native boundary and directly returns a parent whose role is `AXWindow`. The upstream regression test starts from a real application `windowList`, finds a text area, and verifies that text area's `AXWindow` is non-null.

That condition is relevant after a real native window is reachable, but it does **not** source-prove the observed application-level substitution: `AXWindows` itself is AppKit-owned in Qt's design, and the retained value is the application root, not a null descendant `AXWindow`. Applying or upgrading for this fix is therefore not justified as a diagnosis, and no Qt 6.9.1 source-proven fix was found that says `AXWindows` can return the application object.

## Ranked falsifiable hypotheses

1. **Native application/window AX delegation or AX runtime cache is supplying a malformed application relationship** — **medium-high confidence**. Prediction: bounded reads of `AXWindows`, `AXMainWindow`, and `AXFocusedWindow` will consistently identify the root, while a separate native window inventory for the exact PID reports one on-screen window. Support: Qt deliberately leaves those application/window objects to the system, and two retained diagnostics show the root substitution. Contradiction: earlier semantic workflows succeeded, so the app/host combination has previously exposed a usable tree. Minimal discriminator: compare content-free native-window inventory with fresh and reused AX application references.
2. **A timing/state transition left the native window absent from or stale in the AX application registry** — **medium confidence**. Prediction: a bounded timestamped series from fresh `AXUIElementCreateApplication(pid)` references changes from root/none to an `AXWindow`, or differs from a reused reference, without UI input. Support: the canonical artifact is a single snapshot and the bridge is demand-activated. Contradiction: later helper polling timed out and `AXFocusedWindow` already returned a successful (but wrong) value; construction and `show()` precede the event loop. Minimal discriminator: read-only fresh-vs-reused series after independently confirming exact PID/window existence.
3. **The native window exists, but Qt's `QNSView -> accessibleRoot` bridge is absent or its cached interface is invalid** — **medium-low confidence for the root substitution; high relevance if a real window is recovered**. Prediction: the real native window has no semantic view child (or only native chrome), while Qt widget action tests remain valid offline. Support: this is the sole Qt 6.9.1 public ingress to widget semantics, and Qt's cache is lazy/invalidation-sensitive. Contradiction: failure inside this bridge should empty the native window's contents; it does not explain why application-owned `AXWindows` equals the application root. Minimal discriminator: only after obtaining a distinct `AXWindow`, inspect bounded roles/owners/identity for its first-level children.
4. **The app's top-level window lifecycle is absent/hidden/destroyed despite the process remaining alive** — **low confidence**. Prediction: both the AX attributes and an independent content-free native-window inventory show zero windows for the exact executable PID. Support: that state would naturally prevent semantic discovery. Contradiction: the source has a straightforward stack lifetime (`show()` then `exec()`), the AX server reports a focused-window value, and earlier workflows reached controls. Minimal discriminator: exact-PID native window count/bounds only; no title or content capture.
5. **Caller identity/equality handling aliases a valid remote element to the root** — **low confidence**. Prediction: raw type/PID/role remain valid but fresh-process/fresh-reference comparisons disagree with `CFEqual`, or another primary AX client reports a distinct window for the same PID and instant. Support: AX elements are remote proxy objects and prior helper versions timed out. Contradiction: the hardened diagnostic checks CF type, explicit role, owner PID, errors, and equality; both `AXWindows` and `AXFocusedWindow` independently produced the same semantic root. Minimal discriminator: in one bounded helper invocation record fresh-reference cross-equality plus role/PID for each returned object.

Bundle/signing identity is not presently a separate leading hypothesis. Apple's application constructor is PID-based and every returned element's PID matched; direct executable launch also avoids bundle selection ambiguity. Signing/LaunchServices could still influence activation/window registration, but no retained fact or primary source ties it to this exact self-referential result.

The encoding popup discovery failure may share the missing-window/tree ingress only if a distinct native window is recovered but no Qt accessible root appears. Current evidence cannot connect it more specifically.
