# Desktop framework evidence — #132

Accessed **2026-09-19**. Internal research for [ticket #132](https://github.com/connectedloops/safeparts/issues/132), under [Wayfinder #126](https://github.com/connectedloops/safeparts/issues/126). **Not an architecture decision or implementation authorization.**

## Scope and method

Compare Electron (bundled browser), Tauri 2 (system webview), and Qt 6 Widgets (C++ toolkit, without Qt WebEngine). Qt represents the toolkit category because its first-party APIs cover desktop accessibility, clipboard, dialogs, and printing; this is a bounded shortlist, not a finding against Flutter or Avalonia. No existing or retired application implementation was inspected. No reuse assumption enters the comparison.

The approved product serves nontechnical individuals on Windows/macOS/Linux, offline with bundled resources and no app-initiated requests; text and small files; existing-share interoperability; no retained sensitive sessions/history; explicit file export, printing and copy/paste. Exact OS versions, input limits and cleanup guarantees remain decisions. Signing, channel costs and installation policy belong to sibling distribution research.

**F** = documented fact; **I** = inference/design implication, not tested; **U** = unresolved. Sources below are first-party documentation/source fetched in full, not search snippets. Brave Search discovered sources. Tauri's documentation host was unreachable from this environment; its official documentation repository supplied equivalent source pages. Versionless documentation is a moving target: Electron “latest,” Tauri 2 (Rust API displayed 2.11.5), Qt documentation displayed 6.11. Revalidate against pinned versions before implementation.

## What the comparison establishes

- **I:** All three are credible candidates for a small offline desktop tool; documented APIs cover the main interactions, with Tauri printing/accessibility and runtime packaging needing especially explicit cross-platform validation. This is not a ranking.
- **I:** Bundling a runtime trades distribution weight and patch ownership for version control. System webviews trade that control for OS/runtime dependencies and heterogeneous behavior. A Widgets approach removes the browser layer but adds C++/Rust boundary work if Rust is chosen.
- **U:** None of these documents proves the complete product promise of zero app-initiated traffic or no retained sensitive data. Absence of an HTTP plugin is not evidence of absence of all requests. Network denial testing must cover runtime helpers as well as app code.
- **U:** No UI framework establishes Safeparts share compatibility or cryptographic correctness. Later work must test supported existing-format fixtures in both directions, entropy acquisition, malformed inputs, error handling, Unicode/text fidelity and small-file byte fidelity against the agreed contract. This study neither inspects implementations nor chooses algorithms.

## Decision-changing gaps and bounded prototype plan

These are proposed experiments, **not executed tests or permission to build the app**. Use fabricated marker strings only; do not use real secrets/shares.

1. **Offline closure and network boundary.** After a human defines OS/architecture/Linux baselines, run a packaged minimal candidate in clean machines without prerequisites or internet. Then repeat with networking enabled and process-attributed packet/DNS tracing: cold start, idle, input, errors, dialogs, copy, print and shutdown. Attribute app, runtime helper, updater, printer and OS traffic separately. Pass condition needs a human boundary decision: whether user-requested network printing and OS runtime servicing count against the promise. A default bootstrapper cannot satisfy offline first installation [T2]. OS networking exemptions must not be silently invented.
2. **Session-only handling.** Snapshot writable profiles/temp/cache/log/crash directories before/after normal close and forced termination; search for fabricated markers. Exercise export cancellation, failed printing and dialogs. Test that opening again restores no sensitive state/history. **I:** clipboard managers, OS recents, swap/hibernation, crash reporting, printer spools and user-selected synced/network destinations may outlive the app; framework APIs here do not establish control over them. Decide the threat-model boundary before promising deletion. UI/backend copies and JavaScript-managed memory make strong erasure claims particularly unproven.
3. **Accessible completion, not just API presence.** Exercise one input → share-output and one recovery/error flow using keyboard only, NVDA on Windows, VoiceOver on macOS and Orca on Linux; high contrast, scaling and non-Latin text. Check secret-field announcements against the eventual disclosure policy. Tauri needs direct engine-by-engine evidence; Electron/Qt documentation is a capability claim, not acceptance evidence.
4. **Printing as an output contract.** Use long fabricated shares, multiple pages, Unicode, unavailable printers, cancellation and PDF/physical output. Verify no truncation or reordered content, deliberate copy counts, legible page separation and no unintended retained temporary PDF. Tauri's native/JavaScript API distinction [T8] makes this a selection gate. All candidates need actual OS/backend tests.
5. **Integration and maintainability.** Spike a fresh minimal domain boundary (not retired code): binary input, error, cancellation, returned text and owned buffers. Measure copies and peak memory at candidate input limits; verify no sensitive logging. For Electron validate addon ABI packaging per architecture; for Qt validate Rust/C++ ownership and linking; for Tauri validate command permissions and serialization exposure. Pin framework/runtime/plugin versions and prepare a dependency/license inventory. Maintainer capacity and externally delivered security-update cadence remain human inputs.

Stop here: the evidence supports an architecture discussion, but cannot settle cleanup strength, OS coverage, accessibility quality or operating policy without those decisions and bounded prototypes. No exhaustive framework survey, signing-cost analysis or performance/size benchmark was attempted.
