A break-glass secret is used rarely and usually grants elevated access. The procedure should be short enough to run during an incident and strict enough to prevent casual use.

## Example custody model

A platform team needs emergency access to a cloud account if normal identity systems fail. They choose a 3-of-5 plan: five shares exist, and any three can recover.

Suggested custody:

- Share 1: security lead.
- Share 2: operations lead.
- Share 3: engineering manager.
- Share 4: offline company safe.
- Share 5: executive sponsor or compliance custodian.

Three independent participants are required. One unavailable person does not block recovery, and one compromised holder cannot recover alone.

## Setup procedure

<Steps>
1. Learn the workflow with a synthetic drill, including a failed verification. This does not validate the real backup.
2. Generate or export the source Secret in a controlled environment. Keep a known-good working copy until verification succeeds.
3. Split it with the chosen Threshold, Share encoding, and Passphrase protection policy. Save each Recovery share on its intended custody medium and give each custodian only their own share.
4. Record custody, holder contacts, Threshold, and Share encoding without recording sensitive material.
5. Complete the [saved-backup checkpoint](#verify-saved-backup) below using the actual saved material.
6. Restore separated custody and clean up verification material. Only then treat the backup as established and retire the working copy according to policy.
</Steps>

<h2 id="verify-saved-backup">Verify the saved backup</h2>

This checkpoint applies to personal backups too. A synthetic drill teaches the process; only recovery from the actual saved Recovery shares can check the real backup. A successful combine or integrity check alone does not prove that you backed up the intended Secret.

### Prepare the session

- Approve a short session on a trusted, access-restricted machine, offline where practical. If policy cannot permit it, keep the working copy and leave setup incomplete until a safe procedure is approved.
- Use a private workspace on encrypted temporary storage, outside sync and backup folders.
- Disable shell tracing, session recording, screen capture, and clipboard history. Do not use shared CI, support tools, or online comparison services.
- Read back the files actually exported to custody media, or transcribe the actual paper or metal copies. Do not use only the original in-memory split output or aggregate export. Exercise each custody copy of each share in turn.
- Keep the source secret unchanged in a separate private file for comparison.

### Recover and compare each selection

- Bring together exactly the threshold number of distinct shares from the same split. This is approved temporary aggregation, not a storage plan.
- Retrieve the intended passphrase through its separate recovery path, if used. Keep passphrase protection intact.
- Use CLI file input and `--out` to a fresh private file, not terminal output. Never overwrite the source.
- Compare exact bytes locally. In a Unix-like environment, `cmp -s source.bin recovered.bin` returns 0 for identical files, 1 for different files, and another status for an error. Only 0 passes. For Windows, use the [Python comparison procedure](#windows-byte-comparison) below.
- Record only the result, non-sensitive share identifiers, approvals, and time. Do not open the recovered file for visual inspection or print, log, screenshot, or upload secrets, shares, passphrases, recovered bytes, or hashes.

### Cover every saved share

First verify shares 1 through <var>k</var>. Keep the first <var>k</var> minus 1 verified shares as anchors; replace the last share with each remaining share. Recover and compare each selection, removing its temporary selection and recovered file before the next check. This takes <span class="token" dir="ltr">n - k + 1</span> checks.

| Plan | Selections to check |
| --- | --- |
| 2 of 3 | 1/2, then 1/3 |
| 3 of 5 | 1/2/3, then 1/2/4, then 1/2/5 |
| 1 of <var>n</var> | Each share alone |

- Exercise every share intended for custody, including each saved copy.

One passing subset says nothing about untested shares. These checks exercise every saved share, not every possible combination, and do not prove future readability.

### On any failure

Stop on any read error, combine failure, wrong passphrase, byte mismatch, or comparison error.

- Keep the known-good working copy. Correct the saved copy or recreate the backup from the source, then repeat the full checkpoint with corrected saved material.
- Keep passphrase protection intact; do not bypass it to make a check pass.
- For a recreated split, make fresh custody copies. Retire superseded shares only after the replacement passes.
- Before leaving the failed session, perform the cleanup below while preserving the known-good source.

### Restore custody and clean up

- Return custody media to separate holders. Remove temporary selections, aggregate exports, recovered files, and temporary passphrase copies.
- Clear clipboard history and close verification tools.
- Use the approved encrypted-workspace disposal procedure. File deletion alone does not guarantee erasure on SSDs, snapshots, or backups.
- Confirm that no account, device, administrator domain, or transport channel retains enough shares to recover. Keep the passphrase on its separate custody path.
- Only after successful verification and cleanup, retire the source working copy under policy.

Verification necessarily exposes the Secret and a Threshold-sized selection inside the controlled session. If that environment or its cleanup is suspect, treat the Secret as exposed, rotate it, and verify a fresh backup. Routine synthetic drills remain useful after setup, but never replace this checkpoint for a new or rewritten backup.

Practice both outcomes with the [synthetic saved-backup rehearsal](../automation/#saved-backup-rehearsal).

<h3 id="windows-byte-comparison">Exact-byte comparison on Windows</h3>

With Python 3 installed, run this in PowerShell inside the private workspace. Replace only the two file paths. It compares file contents, not timestamps, and prints no secret bytes:

```powershell
py -3 -c "import filecmp, sys; sys.exit(0 if filecmp.cmp(sys.argv[1], sys.argv[2], shallow=False) else 1)" source.bin recovered.bin
$LASTEXITCODE
```

Only exit status 0 passes. A nonzero status or failure to start Python means verification did not pass; follow the failure-retention steps above. Do not share exception output that identifies private paths. The same Python expression works with `python3` on Linux/macOS.

## Recovery procedure

<Steps>
1. Open the incident or emergency change record.
2. Confirm approval according to policy.
3. Collect enough shares to meet the threshold in the recovery environment.
4. Combine the shares and recover the credential.
5. Use the credential only for the approved task.
6. Rotate or disable the recovered credential.
7. Create a new Safeparts split for the replacement credential.
</Steps>

For synthetic command examples, see [automation patterns](../automation/).

:::danger
After break-glass recovery, assume the gathered shares were exposed. Rotate the underlying credential and issue a fresh split.
:::

## Audit record

Record:

- who approved recovery;
- which custodians participated;
- when recovery started and ended;
- which credential or system was recovered;
- what rotation happened afterward.

Do not record share text, passphrases, screenshots of shares, or recovered credentials.
